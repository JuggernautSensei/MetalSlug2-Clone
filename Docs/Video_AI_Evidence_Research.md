# AI 활용 역량 — 참고 채널 조사와 프로젝트 증거 계획

조사일 2026-10-13. 사용자 지정 채널: [생각등대](https://www.youtube.com/@thinklighthouse_company).

## 실제 접근 결과와 남은 조사

YouTube 채널/동영상 페이지를 웹 검색으로 열었으나 fetch throttled로 본문·자막을 읽지 못했다.
이후 공개 원본 HTML을 직접 읽어 채널과 아래 두 영상의 제목·설명란을 확인했다.
한국어 자막 트랙 정보는 있었지만 자막 요청 응답은 비어 있어 대본을 확보하지 못했다.
[생각등대 웹사이트](https://think-lighthouse.com/)도 열었지만 파싱된 본문이 비어 있었다.
따라서 **채널 영상 내용 분석은 미완료**다. 영상 제목이나 2차 AI 요약을 근거로
창작자의 조언을 단정하거나 인용하지 않는다.

원본 제목·설명란을 확인한 영상:
- [이력서에 AI 관련 이거 쓰세요. 더 이상 고민하지마세요](https://www.youtube.com/watch?v=fIxwGWwN93o)
- [취준생 대부분 포트폴리오를 잘못 만들고 있습니다](https://www.youtube.com/watch?v=fu9ZN8-xdnk)

설명란은 전자책/웹사이트 안내와 채널 소개 중심이며 본편의 상세 조언은 제공하지 않는다.
확인한 제목·설명은 `Video/analysis/fIxwGWwN93o-source.txt`,
`Video/analysis/fu9ZN8-xdnk-source.txt`에 기록했다.

검색에서 발견한 추가 확인 후보:
- ‘AI 시대, 회사만 믿는 개발자는 결국 버려집니다 ( 이렇게 준비하세요 )’

마지막 후보 제목은 2차 검색 인덱스의 발견 단서이며 현재 원본 확인/내용 요약이 아니다.
별도의 [첫 번째 직접 동영상 탐색 후보](https://www.youtube.com/watch?v=SsHGSf_nzrI)는
‘물경력 쌓인 개발자가 이직을 위해 반드시 준비해야 할 3가지 방법은?’으로 검색에서 발견됐으나
이 영상 또한 원본 본문을 읽지 못했다. 사용자에게 직접 링크/대본을 요청한다.

## 아래는 채널의 의견이 아닌, 이 코드베이스에 대한 제안

사용자 확인: 2024 게임 전체 직접 구현, 2026 에디터 제작에 바이브 코딩 사용.
에디터의 반복적 UI 작성을 AI로 보조한 사실을 숨기거나, 반대로 모든 설계·검증을 사람이
직접 했다고 추정하지 않는다.
추가 사용자 확인: 필요한 기능을 스킬을 통해 충분히 계획하고 테스트 준비·검증 루프로 제작했다.
AI는 QA하기 좋은 환경을 만드는 데 활용했고 실제 게임 QA는 사용자가 직접 수행했다.
대표 작업의 구체적인 대화/로그/전후 시연은 아직 받지 않았다.
사용자는 참고 채널을 띄엄띄엄 봤으며 특정 영상의 조언을 채택했다고 확인하지 않았다.

AI 사용 역량은 도구 이름보다 작업 통제와 결과 검증의 증거를 보여주는 편이 설득력이 있다.
게임에 생성형 AI 기능을 새로 넣을 필요는 없다. ‘적 AI’와 ‘개발에 사용한 생성형 AI’를 구분한다.

| 역량 필터 | 요청할 증거 | 이 프로젝트 후보 | 피할 표현 |
|---|---|---|---|
| 문제 정의 | 변경 전 문제와 목표를 적은 요청 | 오래된 코드 구조/제작 흐름 정리 | ‘AI로 다 개선했다’ |
| 작업 경계 | 요구사항·규칙·보존 대상 | Assets/JugX/동작 순서/기준선 보존 규칙 | 실제로 지시하지 않은 원칙을 소급 주장 |
| 설계 판단 | 제안 여러 개와 선택 이유 | 과한 추상화 축소, 적 타입별 클래스, 병렬 디코드 경계 | AI가 낸 구조를 무조건 좋은 설계로 소개 |
| 검토·수정 | AI 오류를 발견하고 수정/거절한 대화와 diff | 수치 연산/난수 소비/타입 레이아웃 위험 검토 | ‘AI 코드는 항상 정확’ |
| 검증 설계 | 실행 로그, 커밋, 기준선 | 테스트, 7개 캡처, 튜닝, 텍스처 로딩, SimCheck | 해시 일치를 완전한 동작 증명으로 과장 |
| 반복 작업 | 재현 가능한 스크립트와 사용 과정 | Verify/TraceLoad/Check | 스크립트 존재만으로 실행 성과를 주장 |
| 한계 이해 | 미해결/트레이드오프 기록 | 해시 누락/양자화, 로딩 시간 변화, 재로드 범위 | 근거 없는 ‘몇 배 생산성’ |
| 설명 능력 | 자신이 작성한 원리 설명 | FSM/픽셀 마스크/사운드 voice 관리 | 본인이 설명할 수 없는 용어 나열 |

프로젝트 내 1차 근거:
`Docs/RULES.md:34` 보호 대상, `Docs/RULES.md:49` 검증,
`Docs/ROADMAP.md:56` 해시 한계, `Scripts/Verify.ps1`, `Scripts/TraceLoad.ps1`,
`Tools/SimCheck/Main.cpp:23`, `Source/Render/SpriteBatch.cpp:258`.
문서는 당시 기록일 수 있으며 사용자 실제 지시/참여와 실행 로그를 추가 확인한다.

## 영상에 넣을 분량

P1 초반에는 프로젝트와 구현 범위를 소개하며 개발 연도 구분을 핵심으로 강조하지 않는다.
P3에 45~75초를 배정해 대표 사례 1개를 위 순서로 설명한다.
한글 자막과 다른 원본 플레이를 유지하고, 검증 로그/전후 구조 그림이 필요하면
사용자가 원하는 차분한 스타일의 짧은 보조 화면으로 검토한다.
상세 AI 사례 기록은 영상 설명란/GitHub 문서로 연결한다.

## 사용자 확인 중심 사례

문제: 위치·오프셋의 1~2px 변경에도 재빌드가 필요해 반복 제작이 번거로웠다.
해결: 데이터 기반 씬 저장/로드, 런타임 조정, Claude/ImGui 편집 도구와 핫 리로드.
사람 역할: 필요한 기능과 검증 절차 계획, 부분 장면 재현, 스프라이트 정렬·공격 간격·미사일·히트박스·지형 감각 QA.
AI 역할: 그 QA를 수행하기 좋은 도구 환경의 제작 보조.
성과: 재빌드 없이 세부 조정을 반복할 수 있어 개발이 수월해졌다는 사용자 경험.
미확인: 정확한 시간 절감 수치, 대표 실패·수정 사례의 로그, 영상에 담긴 변경 전후의 구간.

## 확인되지 않은 성과 수치

기존 아키텍처 문서의 줄 수·로딩 시간·테스트 902개·리플레이 15개는 현재 근거로 사용하지 않는다.
현재 ROADMAP에는 테스트 895개와 SimCheck 840개 기록이 있으나 이번 조사에서 재실행하지 않았다.
측정 로그와 대상 커밋을 받은 뒤 자막을 확정한다. 속도·생산성 향상 수치는 추정하지 않는다.
