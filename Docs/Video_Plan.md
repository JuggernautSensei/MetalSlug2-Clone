# MetalSlug2 Clone — 소개 영상 구성안

상태: 요구사항 반영 + 코드/영상 표본 조사. 편집·크롭·자막 합성은 시작하지 않음.
원본은 변경하지 않았고 `Video/analysis/`에 조사용 프레임만 생성했다.

## 1. 확정된 방향

- 현재 목표: 유튜브에서 게임과 구현 소개. 장기 목표: 취업 포트폴리오.
- 제목: MetalSlug2 Clone. 제작자: JuggernautSensei.
- 개발 기간: 2024.02.05~2024.04.05 1차, 2026.10.08~2026.10.13 리팩터링(사용자 제공).
- 자막만, 차분한 기술 소개, 게임 원음 유지. 추가 음악·내레이션은 요청하지 않음.
- P1 전체 플레이 → P2 에디터 시연 → P3 다른 플레이 클립을 이용한 회고.
- P1의 플레이는 시작부터 종료까지 유지. 임의의 하이라이트 편집으로 대체하지 않는다.
- 개발 연도와 리팩터링 시점은 핵심 메시지가 아니다. 필요하면 소개 정보로만 짧게 표시한다.
- 핵심 이야기: 작은 배치·스펙 변경에도 재빌드가 필요했던 불편 → 데이터 기반 씬과 저장/로드 → 런타임 편집·핫 리로드 → 사람이 QA하기 좋은 환경.

## 2. 길이 제안

### 사용자 확인 개발 이력

- 2024: 게임 전체를 직접 구현했다고 사용자 확인.
- 2026: 에디터를 제작. 반복적인 UI/보일러플레이트 작성에 바이브 코딩을 사용했다고 사용자 확인.
- 2026 리팩터링의 AI 사용은 기존 사용자 요구사항에 명시되어 있음.
- 현재 소스의 모든 게임 구조가 2024와 동일하다는 뜻은 아니다. 연도별 상세 변경은 추가 확인.
- 사용자가 필요한 기능을 상세히 계획하고 스킬과 테스트 준비·검증 루프를 이용해 에디터를 제작했다고 확인.
- Claude AI와 ImGui로 도구를 제작하고, 플레이 감각·스프라이트 정렬·시각적 품질의 QA는 사용자가 직접 수행했다고 확인.
- 연도별 이야기를 중심으로 구성하지 않는다. 실제 기여의 구분이 필요할 때만 개발 이력을 사용한다.
- 사용자에게 참고 채널의 특정 영상 선택을 필수로 요구하지 않는다.

P1 약 6분 30초~6분 45초 + P2 약 5~7분 + P3 약 1분 30초~2분.
합계 약 13~16분. 에디터를 크게 다루고 플레이 전체를 유지하면 이 정도가 자연스럽다.
P2는 실제 좋은 시연의 양을 확인해 정한다. 계획 단계의 제안이며 확정 길이가 아니다.

## 3. 원본 조사

모두 1920×1080 / 30fps / H.264 / AAC 오디오.
Source1 4:47.80, Source2 6:45.80, Source3 16:19.16.
Source1/2는 30초 간격, Source3는 45초 간격의 정지 프레임 표본을 확인했다.
전 구간 연속 재생·정밀 버그 검사·오디오 청취를 완료한 상태는 아니다.

| 원본 | 표본에서 확인한 흐름 | 사용 제안 |
|---|---|---|
| Source2 | 시작 IDE → 일반 스테이지 → 차량/적 → 보스 → 6:38에서 종료 배너 진행 | P1 주 후보. 실제 게임 시작/종료 경계와 연속성 정밀 확인 필요 |
| Source3 | 약 0:45 애니메이션, 1:30~3:00 맵, 3:45 충돌 마스크, 5:15~12:45 적/보스 랩, 13:30 이후 플레이 | P2 우선, 뒤쪽 플레이는 P3 후보 |
| Source1 | 스테이지~보스 플레이. 파일명에 bug라고 명시 | P3 후보. 버그 시간과 해결 여부 확인 후 정상 구간만 사용 |

시간은 표본 위치/탐색 후보이지 정확한 편집 in/out이 아니다.
Source3의 3:45 화면에서 Ground Mask의 Pencil/Eraser/Rect/Line/Fill과 빨간 마스크 표시를 확인했다.
보스/적 랩은 상태/박스와 파라미터 창이 함께 나타난다. 이것만으로 실제 변경/저장 성공을 입증하지 않는다.

## 4. 화면 구성과 크롭

Source2 0:30/6:38 표본의 게임 영역은 대략 x=480, y=186, w=960, h=672.
16:9가 아닌 원본 게임 화면 비율이므로 가로세로를 억지로 늘리지 않는다.
전체 구간에서 창 이동/크기 변화를 확인한 뒤 정확한 크롭 값을 확정한다.

권장: 1920×1080 출력 캔버스 안에 게임 화면 비율을 유지해 배치하고,
하단 별도 영역에 1~2줄 자막. HUD·플레이어·보스 공격을 자막이 가리지 않게 한다.
게임 바깥 IDE/콘솔은 P1/P3에서 제외. 에디터에서는 Editor 컨트롤과 작업창을 함께 남긴다.
P2의 detached ImGui 창이 게임 창 밖에 있으므로 게임 창만 크롭하면 시연 UI가 사라진다.

## 5. P1 — 풀 플레이 자막 흐름

게임 장면에 따라 순서를 조정한다. 아래 시간은 완성 영상에서의 대략적인 분량 제안이다.

| 흐름 | 화면 | 자막의 역할 | 후보 기능 |
|---|---|---|---|
| 첫 20~30초 | 게임 시작, 이동/사격 | 이름, 프로젝트 범위, 소개할 구현과 제작 도구를 짧게 안내 | 기본 정보 |
| 초반 1분 | 이동·점프·앉기·조준 | 입력을 액션으로 바꾸고 조작/포즈/공격을 조합하는 방식 | C02~C08 |
| 무기 획득/교체 | 무기마다 달라지는 공격 | 데이터 튜닝과 발사/폭발 처리; 같은 장면에서 사운드도 소개 | C09, W07/W08, A02~A05 |
| 발판·지형 구간 | 점프/착지/낙하 | 픽셀 지형 마스크와 AABB 판정의 역할 구분 | W01~W05 |
| 다양한 적 등장 | 병사/차량/헬기 | FSM의 상태, 거리/쿨다운/확률로 다음 행동 선택 | E01~E05 |
| 전진·새 구역 | 스폰·카메라 변화 | 섹션 트리거, 게이트, 화면 범위 계산, 객체 정리 | S01~S07 |
| 보스전 | 부위/패턴 전환 | 부위별 공격·피격, 상태 전환과 데이터. 마지막은 원음 중심 | E06, A06 |
| 클리어 | 클리어 연출 | 지금부터 그 데이터를 만드는 도구를 보여주겠다는 연결 | P2 연결 |

처음부터 어려웠던 점까지 모두 나열하지 않는다. P1은 동작과 구현 원리,
P2는 제작 과정, P3는 실제 어려움·판단·개선으로 역할을 나눈다.
회고를 플레이 중 짧게 예고하는 것은 가능하나 상세 설명을 반복하지 않는다.

자막 제안: 1~2줄, 보통 5~8초. 복잡한 항목은 문장 2~3개를 차례로 제시한다.
화면에서 볼 행동을 먼저 짚고 원리를 설명한다. 세부 구조/코드 전체는 문서로 연결한다.
수치 개선·역사·감정은 사용자 확인 전 문장으로 확정하지 않는다.

## 6. P2 — 큰 비중의 에디터 시연

### 사용자 확인 문제와 효과

몬스터·오브젝트와 분리된 스프라이트의 위치를 코드에서 조정하면 1~2px 수정에도 재빌드가 필요했다.
씬 구성을 데이터로 옮겨 저장/불러오기와 런타임 변경이 가능해졌고, 이를 직접 조작하고
확인하기 위해 편집 도구를 제작했다. 다음 효과는 사용자 경험이며 정량 측정값은 아직 없다.

- 분리된 유닛/스프라이트 부위의 위치와 오프셋을 픽셀 단위로 맞춤.
- 몬스터·스프라이트 배치 및 애니메이션 클립 작업을 편리하게 수행.
- 공격 간격·미사일 발사·히트박스를 조절하고 핫 리로드해 게임 감각을 반복 확인.
- 전체 스테이지를 플레이하지 않고 필요한 부분을 재현해 직접 QA.
- 내부 그림 도구로 지형 충돌 마스크를 편집해 접지·충돌 감각 조정.

‘모든 필드가 즉시 반영’이라고 확장하지 않고 실제 시연에서 편집→적용 경로를 확인한다.

| 도구 | 분량 제안 | 보여줄 과정 | 전달할 이득 |
|---|---|---|---|
| 애니메이션 편집기 | 60~90초 | 재생 → 느린 프레임 확인 → 피벗/속도 변경 → 미리보기 → 저장 | 프레임 정렬과 반복 조정의 시각화 |
| 스테이지·배치 편집기 | 75~105초 | 섹션 선택 → 오브젝트 이동/복제 → 트리거 확인 → 저장 → 플레이 확인 | 긴 스테이지를 데이터로 배치·관리 |
| 지형 충돌 마스크 편집기 | 60~90초 | 배경/마스크 표시 → 지면 편집 → Undo → 저장 → 접지 결과 | 보이는 지형과 실제 충돌 데이터의 관계 |
| 적 AI·전투 튜닝 랩 | 105~135초 | 적 배치 → Pause/Step → 박스/상태 표시 → 쿨다운/offset/공격 박스 변경 → 재로드 → 결과 | 재빌드 없이 행동과 피격을 관찰하며 튜닝 |

사용 이유 → 변경 전 → 편집 → 저장/재로드 → 변경 후의 순서가 기본이다.
필요한 과정이 원본에 빠져 있으면 추가 촬영을 요청한다. 편집으로 구현되지 않은 결과를 연출하지 않는다.
직렬화는 ‘모든 JSON 원형 보존’으로 묶지 않는다. AnimDocument는 재직렬화,
Stage/Hitbox/Motion은 원문 패치가 확인됐다. 핫 리로드의 적용 대상도 구분해서 설명한다.

## 7. P3 — 별도 플레이로 회고와 AI 역량

다른 원본의 정상 플레이 장면을 배경으로 다음 3개 사례 중 증거가 좋은 것을 선정한다.

1. 입력·상하체·공격 조합을 다루면서 어떤 복잡함을 어떻게 분리했는가.
2. 에디터/데이터 작업 흐름에서 실제로 무엇이 불편했고 무엇을 개선했는가.
3. 필요한 편집 기능을 상세히 계획하고 AI와 테스트·검증 루프로 제작해 직접 QA할 환경을 구성한 사례.

각 사례: **문제 → 선택한 방법 → 본인이 판단한 이유 → 확인 가능한 결과 → 남은 한계**.
마무리: 현재 완성 범위, 배운 점, 이후 목표, GitHub.
GitHub 제공 주소는 프로필이므로 공개 저장소 링크는 별도 요청한다.

AI 설명 초안(사용자 진술 기반, 정확한 시연·로그 연결은 남음):
‘필요한 편집 기능과 테스트·검증 절차를 먼저 계획하고, Claude와 ImGui를 활용해 도구를 제작했습니다.
게임 감각과 시각적 품질의 최종 QA는 직접 수행했습니다. AI에는 QA를 맡기기보다,
필요한 장면을 재현하고 수치를 조정하며 확인할 수 있는 환경을 만드는 역할을 맡겼습니다.’

## 9. 다음 단계
