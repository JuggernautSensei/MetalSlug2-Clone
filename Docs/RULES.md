# RULES — 다음 작업자가 먼저 읽을 규칙

2026-10-13. 구조와 작업 순서는 `ROADMAP.md`에 모은다. 별도 작업 기록 폴더를 만들지 않는다.

## 최우선 요구

1. JugX는 사용자의 스타일 기준이다. 실제 파일을 읽고 구조·이름·소유권·클래스 배치를 따른다.
2. 경량 C++로 작성한다. 필요한 곳에 virtual/override를 사용하고 C 방식 함수 포인터 테이블을 없앤다.
3. 사람이 호출 흐름과 책임을 따라갈 수 있게 작성한다. 범용 프레임워크, 작업 큐, 알림 계층, 서비스를 포인터 묶음으로 운반하는 구조를 늘리지 않는다.
4. 논리적으로 동치이면 파일·클래스·함수를 적극적으로 삭제/통합/재작성해도 된다.
5. 수정 전후의 상태 전이, 입력 소비, 난수 소비, 수치 계산, 이벤트와 렌더 순서를 유지한다. 테스트 통과만으로 동치를 주장하지 않는다.
6. 사용자가 계획 후 즉시 코딩을 요청했다. 통상적인 구현 판단은 자체 진행한다.

## 스타일 맞추기

현재 목적은 사용자가 실제로 작성할 법한 구조를 찾는 것이다. 포맷이나 네이밍을 맞춘 결과만으로 사용자 스타일을 학습했다고 판단하지 않는다. 이 절이 학습 절차와 피드백의 단일 기록이다.

### 기준 자료

- 사용자가 스타일 기준으로 지정한 JugX: `Vendor/JugX/JugX`. 준비 시점 커밋은 `c1efc07`. 작업할 때 현재 버전과 실제 내용을 확인한다.
- `Application.h/.cpp`: 실행 흐름과 생명주기 책임.
- `Event.h/.cpp`: 필요한 다형성과 작은 인터페이스.
- `FileReader.h/.cpp`, `FileReaderWriter.h/.cpp`: API 경계, 실패 처리와 상속의 실제 사용.
- `Scoped.h`, `Timer.h/.cpp`: 소유권과 작은 값/상태의 표현.
- 다른 원본 코드나 백업은 사용자 작성 여부가 확인된 뒤 기준으로 채택한다. 오래된 파일이라는 이유만으로 사용자 원본이라고 추정하지 않는다.
- 현재 게임 Source는 수정 대상이다. 이전 에이전트가 바꾼 코드를 스타일 기준으로 삼지 않는다.

### 진행 순서

1. 작은 책임 하나를 선택하고 현재 호출자·상태·동작 계약을 읽는다. 첫 비교 후보는 `Source/Audio/VoiceAllocator.h/.cpp`다. 외부 오디오 구현과 분리되어 있으며 슬롯 선택·재사용 순서를 한 영역에서 설명할 수 있다.
2. 관련 JugX 코드를 읽고 네이밍/서식 외에 함수 분리, 상태 위치, 소유권, 직접 호출과 추상화의 선택을 비교한다. 관찰에는 파일과 함수 근거를 붙인다.
3. 사용자 요구로 확정된 기준과 새 가설을 구별한다. 가설은 "어떤 상황에서 어떤 형태를 선택하는가"로 표현한다. 클래스 수나 함수 길이 같은 임의의 제한을 만들지 않는다.
4. 선택한 영역만 수정해 실제 diff를 보여준다. 추가한 클래스/함수/중계마다 필요한 이유를 설명하고 더 직접적인 형태도 검토한다. 동작 계약과 선택 순서는 유지한다.
5. 사용자에게 코드에서 맞는 부분과 어색한 부분을 확인받는다. 가능하면 수정 예시를 우선 근거로 삼고, 짧은 피드백만 있어도 구체적인 코드 위치에 연결한다.
6. 확인된 기준과 반례를 아래 기록에 반영한다. 그 기준을 인접한 책임 하나에 적용해 다시 확인한 뒤 전체 작업 계획에 반영한다. 특정 예시의 선택을 프로젝트 전체의 금지 규칙으로 확대하지 않는다.

사용자 피드백은 스타일을 맞추기 위한 입력이다. 통상적인 구현 변경마다 승인 절차를 추가하지 않는다. 검증 실행을 제외한 사용자 요청이 있으면 그 범위에서는 테스트/캡처/빌드를 자동 실행하지 않고 실행하지 않은 항목을 명시한다. 정적 동치 검토와 테스트 결과도 구분한다.

### 피드백 기록

| 판단 영역 | 현재 상태 | 다음에 확인할 내용 |
|---|---|---|
| 라이브러리·이름·enum·인라이닝 | 사용자 요청 확인됨 | JugX 우선, PCH 통합, 이름 충돌 시 대체 평가, Config, 불필요한 enum 기반 타입/forceinline 제거 |
| 읽기 쉬운 구조 | 사용자 목표 확인됨 | 사용자가 읽고 파악하고 설명할 수 있으며 설계 이유가 명확한가 |
| 함수 분리와 직접 작성 | 미확정 | 사용자가 반복을 묶는 시점과 호출 흐름을 읽는 방식 |
| 클래스와 다형성의 경계 | 미확정 | 실제 책임 차이를 표현하는 클래스와 불필요한 추상화의 경계 |
| 상태와 소유권의 배치 | 미확정 | 사용자 예시에서 함께 두는 상태와 분리하는 상태의 기준 |

현재 사용자에게 인정된 수정 예시는 없다. VoiceAllocator.h/.cpp의 첫 제안을 작성했으며 사용자 피드백을 기다린다. 슬롯 선택·기록은 Acquire에서 직접 읽고, 두 경로에서 쓰는 FindOldest_만 보조 함수로 유지했다. 반환/API·슬롯 우선순위·동일 소리 제한·시작 순서 기록 방식은 유지했다. 빌드와 테스트는 사용자 요청에 따라 실행하지 않았다. 이 제안의 분리 수준과 네이밍은 아직 사용자 스타일로 확정하지 않는다.

`VoiceAllocator::Acquire — 피드백 대기 — 단순 기록 중계를 제거하고 선택/기록을 한 함수에서 읽기 — 이 클래스의 슬롯 배정에만 적용하는 가설 — Take_ 제거, 교체 여부를 기존 슬롯 상태에서 읽음`

피드백을 받으면 이 절에 다음 형식으로 짧게 기록한다. 별도 작업 로그는 만들지 않는다.

`대상/함수 — 사용자 피드백 — 적용할 판단 기준 — 적용 범위/반례 — 확인된 예시 또는 diff`

## 사용자에게 확인된 코딩 표준

2026-10-14 피드백. 표준 정리가 우선이며 추가 코드 수정과 JugX 업데이트는 중단한다. 구현 재개는 다음 사용자 요청의 범위에 따른다.

| 대상 | 확인된 기준 |
|---|---|
| PCH | 이미 PCH에 포함된 표준 헤더를 개별 파일에 반복해서 포함하지 않는다. 예: cstdint |
| 감시값 | 무효 인덱스는 JugX의 kInvalidIndex를 우선 사용한다. -1 같은 임의 상수를 대신 쓰지 않는다. 실제 의미가 있는 음수 값과 무효 인덱스를 구별한다. |
| 크기와 개수 | 컨테이너 크기와 항목 개수는 size_t를 사용한다. GetCapacity와 GetActiveCount도 size_t를 반환한다. |
| 인덱싱 | 배열 접근을 위해 불필요한 static_cast<size_t>를 덧붙이지 않는다. 타입 변환은 실제 경계에서 필요한 경우에만 한다. |
| 축약어 | 이름 끝의 축약어는 대문자: _soundID. 중간의 축약어는 단어 형태: _soundIdIndex. |
| 내부 타입 | 내부에서만 쓰는 타입은 private에 둔다. 실제 외부에서 사용하는 반환 타입과 구별한다. |

함수 분리와 클래스 경계는 아직 미확정이다. 위 표준을 확인했다고 기존 VoiceAllocator 제안 전체가 사용자 스타일로 인정된 것은 아니다.

## 기존 코드 스타일 메모

아래는 기존 정리 과정의 작업 규칙이다. 사용자의 설계 취향 전체를 확정한 결과가 아니며, 스타일 맞추기에서 얻은 직접적인 피드백으로 보완한다.

| 대상 | 규칙 |
|---|---|
| class | 함수 위, 데이터 아래; 멤버 데이터는 private |
| struct | 데이터 운반용 public 필드 허용; 함수가 있으면 위에 배치 |
| 헤더 | 선언 한 줄; 값 전달 인자는 const 없음; const&/const* 유지 |
| cpp | 값 전달 인자는 const; 정의의 인자는 줄별로, 함수 사이 빈 줄 하나 |
| 선언 묶음 | 헤더의 연속 선언은 붙이고 기능 경계에만 빈 줄 |
| 생명주기 | JUG_CLASS를 실제 복사/이동 필요에 맞게 사용 |
| 다형성 | virtual/override 사용; final을 쓰지 않음 |
| 소유권 | Scoped 우선; 공유 소유권과 RTTI를 불필요하게 도입하지 않음 |
| 종류 | enum class 우선; 문자열은 데이터 로드 경계에 유지 |
| 주석 | 단위·불변 조건·의도를 짧게; 이력·배너·코드 반복 설명 제거 |
| 실패 | 사전조건은 JUG_ASSERT, 오류 반환은 Result/Error |
| 예외 | try/catch 금지; 외부 라이브러리 경계만 예외 |
| 라이브러리 | JugX에 있는 타입과 함수를 우선 확인 |
| 인라이닝 | 프로젝트 __forceinline 제거; 헤더의 ODR용 inline과 constexpr만 유지 |

참고: `Vendor/JugX/JugX/Application.h`, `Event.h`, `Scoped.h`, `FileReader.h`, `Timer.h`. auto와 람다는 사용자 코드에도 있으므로 전면 금지하지 않는다. 서로 다른 난수 스트림을 전역 하나로 통합하지 않는다.

## 검증

게임 변경 후 빌드와 `Scripts/Verify.ps1`, `Scripts/TraceLoad.ps1`, `Tools/SimCheck/Check.ps1`을 실행한다. 최초 비교점에서 테스트 895개·캡처 7개·튜닝·텍스처 비교가 통과했다. 동치 변경의 실패를 덮기 위해 기준선을 갱신하지 않는다.

AI 전용 SimCheck는 별도 프로젝트에서 게임 Source를 컴파일하되 Main/App를 제외한다. 780개의 고정 입력 체크포인트를 비교한다. 최초 840개 중 사용자가 삭제한 sluglab의 60개만 제외했다. 게임에 검증용 리플레이/CLI를 다시 넣거나 README에 이 도구를 설명하지 않는다. 해시의 누락·양자화 한계는 ROADMAP에 명시한다.

각 변경의 동치 근거는 코드와 diff에서 확인 가능해야 한다. 함수 본문 이동은 토큰 대조, 기본 처리 이동은 동일한 분기·쓰기 순서 대조, 타입 교체는 기본값/레이아웃/반올림/난수 호출을 확인한다.

## 주의점

- MemoryView/MutableMemoryView 값 인자에서 const 제거는 JugX 템플릿 생성자 선택을 바꿀 수 있다. 선언과 정의를 무작정 치환하지 않는다.
- JugX.h를 넣으면 Windows.h의 GetObject 매크로와 JSON 메서드가 충돌할 수 있다. 라이브러리 API의 GetObject에 한해서 Windows 매크로를 undef한다. 게임의 FindEnemy/DrawString, 테스트의 GetLoadMessage는 용도가 다른 기능이므로 이름을 변경했다.
- PCH는 JugX/JugX.h + using namespace jug로 통합했다. 자체 RGBA는 제거했다. 사용처는 r/g/b/a를 명시적으로 초기화하고 채널별로 사용한다. JugX RGBA의 packed 저장 영역이나 equality를 게임에서 사용하지 않는다. 이름 충돌은 JugX 대체 가능성을 먼저 검토한 뒤 게임 이름을 변경한다.
- Random<float>는 이전 RandRange의 uint64→double→float 순서와 다르다. 소품 난수는 Random<double> 뒤 float 변환을 유지한다.
- uidemo 캡처는 벽시계 영향이 있다. 재시도 성공을 완전 동치의 증명으로 쓰지 않는다.
- SimCheck/게임/테스트를 빌드하는 중 소스 파일을 수정하지 않는다. 실행 중인 검증이 끝난 뒤 다음 코드 변경을 한다.

## 가독성 판단

작성자가 읽고 구조를 파악하며 설계 이유를 설명할 수 있어야 한다. 줄 수나 파일 수만 줄이지 않는다. 추가 클래스/함수는 실제 상태 소유권이나 동작 차이를 설명해야 한다. 불필요한 중계·미사용 API를 남기지 않는다.

설정 이름은 Config로 쓴다. enum class는 기반 타입을 생략하는 것을 기본으로 하고, 저장 형식·비트셋의 폭이 필요한 경계만 명시한다. eAction은 IndexedFlags의 16비트 입력 저장 폭을 유지한다. 해시 형식의 폭은 HashState 경계에서 변환한다.
